# 실기기 뷰포트 보정 (Phase 3 후속)

## Context

Phase 3(PR #6, 2026-09-04 머지) 뒤 프리뷰를 실기기에서 보니 **검색·칩 아래부터 바텀시트 위까지, 지도가 실제로 보이는 부분("보이는 지도")이 크롬 개발자도구에서 볼 때보다 훨씬 좁다.** 스크린샷 3장(네이버 인앱 / 크롬 시크릿 / 사파리)으로 원인을 숫자로 확인했다.

시트가 `40dvh`라 시트 상단 위치로 실제 뷰포트를 역산할 수 있다:

| | 시트 상단 | **실제 뷰포트** | 상단 스택 | **보이는 지도** |
|---|---|---|---|---|
| DevTools 390×844 | 506 | **844** | 72 (고정) | **438px** |
| 사파리 | 421 | **702** | 72 (고정) | **353px** (−19%) |
| 네이버 인앱 | 419 | **694** | 72 (고정) | **353px** |
| 크롬 시크릿 | 394 | **656** | 72 (고정) | **324px** (−26%) |

**뷰포트가 142px 줄 때 시트는 비례라 57px만 줄고, 상단 스택 72px은 고정이라 하나도 안 준다. 남은 손실을 보이는 지도가 전부 흡수한다.** 게다가 그 위에 칩 행(~70px)과 FAB 줄(~60px)이 또 고정 크기로 얹혀서, 아무것도 안 가린 지도는 368 → 254px(**−31%**)이 된다.

DevTools가 844px를 그대로 주는 건 브라우저 UI를 시뮬레이션하지 않기 때문이다. **실기기는 656~702px만 준다.** 지금까지의 320/390/430 확인이 전부 이 잘못된 높이 위에서 이뤄졌다.

의도한 결과: 실기기에서 보이는 지도를 되찾고, 같은 착시가 Phase 4(신규 패널·내 활동·리뷰 폼)·Phase 5(데스크탑)에서 반복되지 않도록 검증 기준을 규칙으로 승격한다.

## 확정된 결정 (사용자)

- **검색 블록을 칩처럼 플로팅으로.** 불투명 흰 판(72px)을 없애고 지도가 뒤로 비치게 → 보이는 지도 353 → 421px.
- **검색바 모양은 둥글게(라운드).** 지도 위 레이어라 칩 행과 같은 층으로 읽혀야 한다.
- **거리 `294km` 문제는 그대로 둔다.** (`use-map-screen.ts:192`의 `origin`이 서울 밖 `userLocation`을 그대로 쓰는 건 확인했으나 이번 범위 밖)

## 작업 (커밋 단위 = 한 턴)

브랜치: `fix/device-viewport` (main에서 분기 — 로컬 main이 origin보다 1 뒤라 먼저 pull)

### 1. `viewport-fit: cover` — 죽어 있는 safe-area 되살리기

`app/layout.tsx:9`의 `viewport`에 `viewportFit: "cover"`가 없다. **`env(safe-area-inset-*)`는 `viewport-fit: cover` 없이는 항상 0을 반환**하므로, `app/globals.css:155-159`에 정의된 safe-area 토큰 4개(`--spacing-safe-top`, `--spacing-safe-bottom`, `--spacing-safe-top-or-3`, `--spacing-safe-bottom-or-3`)가 지금 전부 죽어 있다. 스크린샷에서 시트 마지막 카드가 하단 브라우저 UI에 잘리는 것과 직결된다.

- `app/layout.tsx` — `viewportFit: "cover"` 추가
- 시트 본문 하단에 `--spacing-safe-bottom-or-3` 적용 (`app/globals.css`의 `.saeu-sheet__body`)
- **먼저 해야 한다**: `cover`는 `dvh`를 safe-area만큼 키우므로 이후 모든 측정의 기준이 바뀐다.
- 실기기 확인 필수: 인앱 브라우저(네이버·구글)에서의 `cover` 동작은 사파리와 다를 수 있다.
- `docs/decisions.md`에 기록

### 2. 검색 블록 플로팅 (핵심)

`SearchBar`는 `map-screen.tsx:135` **한 곳에서만** 쓰인다 — 새 컴포넌트 불필요. 반면 불투명 상단 블록 마크업(`bg-bg px-5 pt-safe-top-or-3 pb-3 shadow-float`)은 **3개 파일에 복제**돼 있어 같이 바꿔야 스켈레톤 → 실제 전환에서 화면이 안 튄다.

- `components/map-screen/search-bar.tsx:32` — 껍데기를 `rounded-8 bg-bg-sunken` → 떠 있는 알약(`rounded-max bg-bg shadow-float`)으로. 라운드는 pill 제안, `rounded-20`이 대안 (리뷰에서 확정)
- `components/map-screen/map-screen.tsx:134` — 불투명 래퍼의 `bg-bg`·`shadow-float` 제거, 패딩만 남김

- 나머지 4곳(`address-search.tsx:69`, `step-name.tsx:78`, `ui/text-field.tsx:25` 등)의 `rounded-8 bg-bg-sunken`은 **시트 안 입력이라 그대로 둔다**
- `docs/design.md` 화면 1 + `docs/decisions.md` 갱신

### 3. 첫 화면의 지도 위치를 "보이는 지도의 한가운데"로

**지도 중심이 화면 정중앙에 맞춰져 있는데, 정작 보이는 지도의 한가운데는 거기가 아니다.** `use-map-screen.ts:623`이 `initialCenter`를 `SEOUL_CENTER`로 넘기면 SDK는 그걸 화면 정중앙(702px 기준 y=351)에 놓는다. 그런데 보이는 지도는 72~421 구간이라 한가운데가 y=246 — **105px 아래로 치우친다.**

세 스크린샷 모두에서 서울특별시청 마커가 그 한가운데보다 90~100px 아래에 있어 계산과 맞는다(사파리 ~90, 네이버 ~99). 그래서 지도 위쪽 절반은 북한산·성북구 빈 땅이고, 가게가 몰린 아래쪽은 시트가 먹는다. 뷰포트가 작을수록 어긋남의 비중이 커진다 — 스크린샷마다 잘리는 마커가 다른 건 뷰포트 높이가 셋 다 달라 보여주는 영역 자체가 달라서일 뿐, 원인은 이 하나다.

새 로직이 아니라 **재사용**이다. `visibleStripCenterY`(245-256줄)가 이미 그 한가운데를 계산해 카드·마커 탭에 쓰이는데 첫 화면에는 안 걸려 있다.

- `components/map-screen/use-map-screen.ts` — 초기 지도 위치가 `visibleStripCenterY`를 거치게. `/place/[id]` 직접 진입은 이미 그렇게 하고 있으므로(257-262줄 부근) 같은 경로로 모은다
- 같은 어긋남이 `submitSearch`(360-361줄)에는 패딩으로 이미 반영돼 있다 — 초기 fit·뷰포트 변경도 같은 값을 쓰게 통일. 호출자가 3곳이 되므로 추출이 정당하다(코드 최소주의 사다리 5)
- bottom 패딩에 FAB 줄 높이(40px + 여백) 포함 — 3651에서 `[+ 제보]`가 레드 클러스터 마커를 덮는데 둘 다 브랜드 레드 원이라 구분이 안 된다

### 4. 높이 소스 일원화 (확인 후 판단)

CSS는 `dvh`, JS는 `window.innerHeight`로 소스가 둘이다(`bottom-sheet.tsx:258,340,374`, `use-map-screen.ts:253,361,494`). 정상 상태에선 대체로 일치하지만 **키보드가 뜨면 갈린다** — 제보 3단계 입력·주소 검색이 그 자리고, Phase 4의 리뷰 작성 폼이 같은 자리를 다시 만든다.

- **먼저 실기기에서 재현되는지 확인한다.** 재현 안 되면 이 커밋은 건너뛰고 백로그로.
- 재현되면: `interactiveWidget` 설정 또는 실측 소스 하나로 통일

### 5. 규칙 승격 (문서만)

이번 건의 근본 원인은 **검증 기준이 뷰포트 폭만 정하고 높이를 안 정한 것**이다. 이걸 안 박으면 Phase 4·5에서 그대로 반복된다.

- `CLAUDE.md` — "확인은 320/390/430" → **실기기 등가 높이 명시**(390×844 금지, 390×700·390×660 사용). "반응형" 절과 "UI 완성 기준" 양쪽
- `docs/design.md` 공통 블록 — 세로 예산 표(실기기 가용 높이, 상단 스택·시트·오버레이가 각각 먹는 px)
- `docs/decisions.md` — 2026-09-04 항목으로 위 결정 전부
- `docs/roadmap.md` Phase 3 — 비어 있는 `결과:` 줄 채우기 (Phase 0·1·2는 다 있음)

### 6. (조건부) 시트 요약 높이 — 2·3번 확인 후에만

시트를 더 내릴지 논의했으나 **2·3번을 먼저 하고 실기기에서 다시 보기로 했다.** 동시에 바꾸면 무엇이 효과였는지 구분할 수 없다.

지금 702px에서 시트 요약 281px의 내역:

| | px | |
|---|---|---|
| 헤더 (`--sheet-header-h`) | 88 | `{구} {N}곳` + 정렬 트리거 + `SeasonCounter` 라이브 캡션 |
| 이벤트 카드 (`place-sheet.tsx:170`) | ~70 | 본문 첫 항목, `py-3` + 32px 아이콘 |
| **실제 가게 카드** | **~123** | 1.3장 |

**헤더 + 이벤트 카드가 158px(56%)를 먹는다.** 40dvh → 32dvh(225px)로 내리면 카드가 반 장만 남아 "아래 목록이 더 있다"는 어포던스(사파리 스크린샷의 반쯤 잘린 "바다해장집")가 사라진다.

2·3번 뒤에도 지도가 부족하면 **시트 전체를 내리는 것보다 헤더 88px를 줄이거나 이벤트 카드를 첫 자리에서 빼는 쪽**이 카드를 지키면서 같은 픽셀을 번다. 그 판단은 실기기 확인 뒤에.
